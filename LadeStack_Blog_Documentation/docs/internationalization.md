# Internationalization (i18n) and Translation Strategy

## Supported languages (locked)

| Code | Language | Public prefix | Remarks |
|---|---|---|---|
| `en` | English | none | Default and editorial source language |
| `ja` | Japanese | `/ja/` | Font, line breaking and typography QA |
| `ko` | Korean | `/ko/` | CJK typography QA |
| `zh` | Chinese | `/zh/` | House script preference pending confirmation; don't invent region variant |
| `ru` | Russian | `/ru/` | Cyrillic font support |
| `tr` | Turkish | `/tr/` | Turkish case handling, dotted/dotless I |
| `fr` | French | `/fr/` | Accents and longer labels |
| `pt` | Portuguese | `/pt/` | Region-neutral URL; agree house locale conventions |
| `es` | Spanish | `/es/` | Accents, text length |

## Separate two types of translations

**Interface translation** includes navigation, categories, form labels, errors, search, dates, pagination, accessibility strings, menus and footer. All nine must exist on launch. **Article translation** includes the full body, local title, summary, description, headings, alt text and editorial terms. Article translations can publish progressively, subject to review. Never display an English body under `/fr/posts/` while signaling that it is French.

## Route policy

English homepage `/`; other homepages `/{locale}/`. English articles `/posts/{slug}/`, non-English `/{locale}/posts/{slug}/`. Categories, tags, listings, search and utility routes follow the same prefix scheme. URLs are generated by centralized helpers rather than string concatenation spread across components.

Use Astro built-in i18n config where compatible. Ensure file-based route templates and localized route generation actually match the installed Astro version. Test that `/en/` is not generated as a duplicate. Decide consistent trailing slash handling and permanently redirect noncanonical forms where hosting allows.

## Translation identity and groups

Every `.md` stores `articleId`, `translationKey`, `lang`, `slug`. Group published versions by `translationKey`. Language switcher on an article uses only that group's real published versions. For unavailable target locale, either hide/disable its option with clear accessible explanation or take the reader to that language's home/listing with a clearly worded message; **never redirect invisibly to a different article**.

Example group:

```yaml
translationKey: astro-seo-basics
published:
  en: /posts/astro-seo-basics/
  ja: /ja/posts/astro-seo-basics/
  fr: /fr/posts/guide-seo-astro/
not_published: [ko, zh, ru, tr, pt, es]
```

## Locale handling in application

- Use an explicit `locales` registry and `isValidLocale()` guard.
- HTML root gets the correct `lang` value for *every* generated page.
- UI strings read from locale dictionaries with type-complete keys; fallback behavior during development must be visible in QA, not silently mask missing production translations.
- Date/time and number formatting use `Intl.DateTimeFormat`/`Intl.NumberFormat` with locale settings. Stable structured-data timestamps remain ISO strings.
- Screen reader labels, alt texts and aria-live announcements are translated.
- Search uses document `html lang` so Pagefind selects the matching language index.
- `dir="ltr"` for all nine current locales; architecture should not block RTL if future expansion occurs.

## hreflang coupling

The same translation registry supplies article locale switch and SEO alternates. If a French translated article is added tomorrow, all published variants will automatically include the French URL in their respective metadata after rebuild. No per-file hardcoded `hreflang` entries.

Each localized page is self canonical. Reciprocal alternate tags list itself and all other actually published/indexable variants. Do not include draft/review/missing translations. For static utility/category homepages, list alternates only when equivalent meaningful localized pages exist.

## Translation quality workflow

1. Publish accurate original content and verifiable references.
2. Create target `.md` with same identity/category, target `lang`, localized slug and body.
3. Translate contextual meaning, not literal word-by-word fragments.
4. Verify figures, units, proper nouns, acronyms, citations, quoted material and all links.
5. Review local grammar, culturally sensitive framing, alt text and SEO metadata.
6. Set status to `published` only after review; deploy normally through Git push.
7. When source changes materially, flag existing translations for re-review; do not silently assume they remain equivalent.

## Edge cases to test

- English-only story; translated story with 2/9 versions; fully translated story with 9/9 versions.
- Title long enough to wrap on mobile; Japanese and Korean headings, Russian and Turkish tags.
- Two stories share similar translated titles but have different IDs/slugs.
- A variant is unpublished/removed and alternates drop it on next build.
- Localized article not yet present: do not generate a translated stub or 200 response.
- Search on `/fr/` never shows unrelated English-only articles as French results.

## Editorial naming guidance

UI language names should be displayed natively where appropriate (e.g. 日本語, 한국어, Русский) and remain accessible by full descriptive labels. Avoid assuming IP-based language redirects. A reader must always be able to explicitly switch locale and retain a stable URL suitable for sharing.
